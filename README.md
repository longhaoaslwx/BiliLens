# BiliLens

**B 站用户画像与线索复核工具** —— 一套 MV3 源码，同时产出 Chrome / Edge 扩展与 Bilibili Evolved 组件。

[![License](https://img.shields.io/badge/license-MIT-3da639.svg)](./LICENSE)
[![Manifest V3](https://img.shields.io/badge/manifest-v3-4285f4.svg)](https://developer.chrome.com/docs/extensions/develop/migrate)
[![Platform](https://img.shields.io/badge/platform-Chrome%20%7C%20Edge%20%7C%20Evolved-ff6699.svg)](#1-安装)
[![Version](https://img.shields.io/badge/version-1.5.4-informational.svg)](https://github.com/longhaoaslwx/BiliLens/releases/latest)
[![Data](https://img.shields.io/badge/data-stays%20local-2ea44f.svg)](#7-合规边界)

基于 B 站公开数据为用户建立**可复核的画像**：从评论区批量样本中提取组织化行为线索，把同一 UID 在若干第三方公开数据源中的记录取回、清洗、缓存、可视化，再融合进同一条证据链。

- **输入**：UID、`space.bilibili.com` 链接、昵称，或一个 BV 号。
- **输出**：可解释的线索优先级、逐条命中的证据、每个数据源的实际请求端点与采集时间。
- **不做什么**：不使用登录凭证、不绕过风控、不做去匿名化人肉、不上传任何数据。

> **这是线索整理工具，不是身份识别工具。** 所有评分都是**可解释的优先级排序**，不构成事实结论；第三方聚合数据（含弹幕行为记录）同样不代表官方事实，需要人工回到原始证据复核。

> **仓库数据说明**：本仓库**不含任何真实用户的采集样本**（弹幕历史、评论、粉丝牌、曾用名、直播间记录一个都没有），也**不放界面截图**——界面里全是真实样本，截图即泄露。测试断言只用两类数据：内联的合成样本，以及 B 站官方公开测试账号与占位 UID。开发期核对接口用的原始响应留在本地 `.research/`，已在 `.gitignore` 排除。

## 1. 安装

### 1.1 下载安装（推荐）

到 [Releases](https://github.com/longhaoaslwx/BiliLens/releases/latest) 下载对应文件，按浏览器选一个：

| 下载 | 适用 | 怎么装 |
| --- | --- | --- |
| `BiliLens-chrome-v1.5.4.zip` | Chrome 及 Chromium 内核浏览器 | 解压 → `chrome://extensions` → 开发者模式 → 加载已解压的扩展程序 |
| `BiliLens-edge-v1.5.4.zip` | Microsoft Edge | 解压 → `edge://extensions` → 开发人员模式 → 加载解压缩的扩展 |
| `BiliLens-evolved-v1.5.4.zip` | 已安装 Bilibili Evolved | 取包内 `BiliLens.evolved.component.js`，按 [1.2](#12-安装-bilibili-evolved-组件) 安装 |

两个扩展包功能完全一致，仅 `manifest.description` 里的目标标注不同。Edge 与 Chrome 同为 MV3，不需要 Firefox 的 `browser_specific_settings`。

安装后建议打开一个 `www.bilibili.com` 页面并保持标签页存在：评论类接口需要来自该页面的 Referer，页面内请求通道成功率显著更高。

### 1.2 安装 Bilibili Evolved 组件

组件是**独立形态**，不需要装上面的扩展；两者也可以共存（互不通信、各存各的缓存）。

1. 确认浏览器已装 [Bilibili Evolved](https://github.com/the1812/Bilibili-Evolved)（用户脚本管理器 + 脚本本体）。
2. 打开 Evolved 设置面板 →「组件」→「安装组件」→「从文件安装」，选 Release 包里的 `BiliLens.evolved.component.js`。
3. 刷新 B 站页面，右下角出现 **BL** 圆形按钮即生效。

组件选项在 Evolved 设置面板中本组件的条目下：弹幕历史最大页数、每页场次、隐藏仅入场、本地筛选起止日期、单请求超时、缓存 TTL、脱敏与启用站点列表；改完刷新页面生效。组件通过 `GM_xmlhttpRequest` 跨域取数（不可用时降级为页面 `fetch`），缓存写在本机 `localStorage`，不上传数据。

### 1.3 从源码构建

只想用的话不需要这一步，改代码才需要：Node 18+ 与 Python 3.9+（构建脚本只用标准库，无第三方依赖）。

```bash
git clone https://github.com/longhaoaslwx/BiliLens.git
cd BiliLens
python build.py           # 生成图标、双端目录与 zip、Evolved 组件包，并校验全部 JSON
node build-evolved.mjs    # 仅重建 Evolved 单文件组件
```

产物都在 `dist/`：`dist/chrome/BiliLens`、`dist/edge/BiliLens` 可直接「加载已解压的扩展程序」，`dist/evolved/BiliLens.evolved.component.js` 是组件单文件。

改完核心逻辑建议跑一遍离线自检——三个脚本都不依赖浏览器、不发真实网络请求：

```bash
node verify.mjs           # MD5 / WBI / 画像规则 / 群体线索 / 多源解析 / 清洗层 / 完整画像 / 刷屏判定
node smoke.mjs            # 模拟接口响应跑通后台消息路由（七项聚合、清洗口径、单站刷新、导出）
node verify-evolved.mjs   # vm 模拟 Evolved 沙箱 + DOM，端到端验证组件导出与五个标签页
```

## 2. 功能

| 能力 | 它能做什么 | 细节 |
| --- | --- | --- |
| **单用户画像** | UID / 空间链接 / 昵称 → 官方档案 + 投稿行为 + 11 条可解释线索规则，每条给触发证据 | [2.1](#21-单用户画像) |
| **评论区批量分析** | 一个 BV 号 → 前 N 页评论者逐个画像，再按重复话术 / 同头像 / 同签名 / 时间聚集聚出跨账号关联簇 | [2.2](#22-评论区批量分析) |
| **弹幕行为画像** | 读 Danmakus 公开 `/history`，在本机聚合时段 / 活跃日 / 直播间 / 重复文本，不搬运其结论 | [2.5](#25-弹幕行为画像danmakus-analyze-维度本机聚合) |
| **完整聚合画像** | 对齐官方 `/analyze` 的全部维度：五维分类、频道偏好、支持方式、活跃节律、粉丝牌与曾用名 | [2.6](#26-数据清洗与完整聚合画像v130) |
| **独轮车判定** | 同一窗口内大量重复 / 高相似弹幕 → 判刷屏攻击而非「喜爱主播」，按直播间主播归属 | [2.8](#28-独轮车--刷屏判定v154) |
| **多源聚合** | 同一 UID 送 7 个站点真实取数（不是只开链接），本机缓存、逐站留痕、交叉核对 | [2.4](#24-多源聚合biliscope-风格在-xxx-查看) |
| **证据导出** | JSON 全量报告 / CSV 扁平表 / 一键脱敏 / 单文件离线静态网页报告 | [2.3](#23-证据链导出与本地数据) · [2.7](#27-展示分层与纯静态网页报告v140) |

核心原则：**先清洗，再统计，再展示**。第三方原始数据必须先过规范化 → 缺失值 → 异常值 → 去重四道工序（`lib/clean.js`），才允许进入聚合与任何一张图表；每道工序逐项计数，结果可作为「清洗报告」导出复核。

### 2.1 单用户画像

输入 UID、`space.bilibili.com/<UID>` 链接或昵称。昵称经 WBI 签名的用户检索接口解析为 UID（失败时提示直接填 UID）。采集内容：

- **基础档案**：昵称、性别、等级、粉丝、关注、签名、头像、官方认证、大会员标识、勋章、专栏数、注册时间（若平台提供）
- **内容行为**：投稿总数、最近投稿标题/分区/播放/评论/发布时间，以及标题模板率、短时集中投稿次数、夜间投稿占比、平均播放
- **线索评分**：11 条可解释规则 + 2 条可选第三方佐证规则，逐条给出触发证据与权重
- **可复核性**：每个数据源记录接口路径、成功/失败、错误码与采集时间

B 站页面上还有一个右下角浮动入口，可一键对当前用户或当前视频做简要画像。

### 2.2 评论区批量分析

输入 BV 号 / av 号 / 视频链接，抓取前 N 页评论，按去重评论者逐个画像，再输出：

- 账号列表（按线索分排序，点击任一行可对该账号做含投稿列表的深度采集）
- 跨账号关联线索簇：重复话术、相同头像 URL、相同签名、评论时间聚集、低等级低粉丝同质账号
- 每个簇保留原始证据（`rpid`、时间、原文片段）与明确的复核警示
- 样本偏差说明：只覆盖前 N 位评论者，未覆盖人数明确列出

### 2.3 证据链导出与本地数据

- JSON：完整报告（画像、派生统计、规则命中、数据源、评论原文、线索簇及其证据、弹幕记录样本、逐站原始结果、已知局限）
- CSV：扁平账号表（含分数、分档、命中规则 ID、数据覆盖、多源指标与弹幕样本范围、主页链接）
- 可选导出脱敏：移除昵称、评论原文、投稿文本、簇证据，以及弹幕记录样本 / 重复文本 / 直播间名称与逐站原始结果
- 数据仅存 `chrome.storage.local`，设置页可查看占用并一键清除

### 2.4 多源聚合（BiliScope 风格「在 XXX 查看」）

在「多源数据」标签页输入 UID，插件把同一个 UID 送到截图中识别出的站点，实际取回公开数据、写入本机缓存，再与官方画像融合：

| 查询项 | 作用 | 取回的数据 |
| --- | --- | --- |
| 哔哩哔哩 | 官方档案 | 已在主画像采集，仅作交叉核对入口，不重复请求 |
| Danmakus | 成分 / 关注主播 | 关注主播数、标签频次、累计弹幕、直播场次、Top 主播 |
| **Danmakus · 弹幕行为** | **弹幕行为画像** | **公开 `/history` 记录，在扩展本机聚合为时段 / 活跃日 / 事件类型 / 直播间 / 重复文本 / 所涉主播与直播规模（见 2.5）** |
| AICU | 历史评论 | 站点标注的历史评论总量、评论样本、月份 / 24 小时分布、涉及动态数 |
| ICU（matsuri.icu） | 频道页 | 实测纯客户端渲染，只记录页面可达性并给出人工核验链接 |
| ZeroRoku | 粉丝趋势 | 页面 `__NUXT_DATA__` 中的粉丝趋势序列、最新粉丝、近 30 点增量、打赏记录 |
| VTBs（vtbs.moe） | V 圈收录 | 是否被收录、投稿数、舰团记录；普通 UID 返回 404 记为「未收录」而非失败 |

- **真实取数**：不是只打开链接。每个站点记录实际请求端点、HTTP 状态、耗时与采集时间，结果在「站点状态矩阵」中可逐项展开；单站支持「强制忽略缓存刷新」。
- **本地缓存**：逐站缓存键 `bililens:cache:fed:{siteId}:{uid}`，默认 60 分钟，可在设置页调整；只缓存裁剪后的事实与证据片段，不缓存整页 HTML。「清除多源缓存」只删这一类键，保留设置与报告。
- **可视化**：站点状态环图、粉丝趋势折线、评论月份与 24 小时柱状分布、关注主播标签横向条、弹幕行为画像（见 2.5）、站点状态矩阵、第三方关键指标卡、原始证据片段。图表只描述已取回的样本，跨站数据不归一化、不相加。
- **画像融合**：`profile.federated` 是独立的第三方证据层，不改写官方 `facts`。默认**不参与评分**；设置页开启后 F01 / F02 才计入线索分，且必须回到报告人工核验。
- **可复核性**：每个站点提供「人工核验 ↗」链接、实际请求端点与采集时间；导出 JSON 保留 `extra.federated.rawResults` 完整逐站结果，导出可选脱敏。

### 2.5 弹幕行为画像（Danmakus /analyze 维度，本机聚合）

Danmakus 的 `/analyze/{uid}?start=…&end=…` 页面提供服务端聚合画像。本插件**不搬运其前端源码、不调用其分析任务接口、不采用其结果里的主观性格标签**，而是只读取同一数据源的公开原始记录，在扩展本地重算一组可复核的统计：

| 维度 | 计算口径 |
| --- | --- |
| 场次覆盖 | `sessionFetched / sessionTotal`、页数、`hasMore`；明确标注「样本非全量」 |
| 时段分布 | 按 `record.ts`（毫秒）换算到 UTC+8 自然日，分 24 小时 / 星期 / 月份桶 |
| 活跃度 | 活跃天数、每日记录数、最长连续活跃天数、最早 / 最晚记录时间 |
| 事件类型 | 按站点原始 `type` 枚举计数（弹幕 / 礼物 / 大航海 / 醒目留言 / 入场 …） |
| 直播间与分区 | 按 `channel.uId` 聚合记录数 Top 10；按 `live.parentArea` 统计场次 |
| 重复文本 | 归一化（全角转半角、去表情标记、折叠空白、数字替换为 `#`、小写）后只计数，不做语义或倾向判断 |
| 所涉直播间 | 从记录附带的 `channel` / `live` 字段提取主播标签、粉丝量级、机构类型、直播规模（观看人次 / 峰值在线 / 付费人次），主播按场次去重 |
| 原始样本 | 最多 20 条记录（时间 / 类型 / 直播间 / 标题 / 原文），受脱敏开关控制 |

> **重要口径**：「所涉直播间画像」描述的是**该用户出现过的主播与直播间**的属性，不是该用户自己的属性；不能用来推断用户身份、消费能力或立场。界面、导出与 `channelMetaNote` 均带此提示。该维度来自 2026-11-08 对 Danmakus 官方 `danmaku-history.js` 组件的核对（见 3.3）。

设置页可调整：起始 / 结束日期（`YYYY-MM-DD`）、最多取回页数（1–5）、每页场次数（10–50）、是否隐藏「仅有入场记录」的场次。**实测服务端 `/history` 忽略 `start/end` 与 `startTime/endTime`**，日期范围由本工具按 `ts` 在本地筛选，界面会同时显示「本地筛选范围」与「样本非全量」提示，不会把筛选后的子集伪装成全量。

事件类型枚举（保留数字便于站点改版时追溯）：

```text
0 弹幕 · 1 礼物 · 2 大航海 · 3 醒目留言 · 4 入场 · 5 标题变更 · 6 分区变更
7 直播暂停 · 8 直播继续 · 9 禁言 · 10 警告 · 11 录制开始 · 12 录制中断 · 13 主播
```

弹幕行为统计**不参与线索评分**，只作为证据与可视化；它不是 Danmakus 官方画像结论，也不构成身份认定或行为定性。v1.3.0 起该画像已扩展为完整 `/analyze` 维度，见 2.6。

### 2.6 数据清洗与完整聚合画像（v1.3.0）

**所有图表只有一个数据入口。** 第三方原始响应不再被任何图表直接遍历，必须先在 `lib/clean.js` 中经过四道固定工序：

| 顺序 | 工序 | 规则 |
| --- | --- | --- |
| 1 | 字段规范化 | 统一 v2 / v3 结构、ID 类型、时间戳单位（秒 → 毫秒）、文本全半角与数组字段 |
| 2 | 缺失值处理 | **缺失 ≠ 0**：数值缺失记为 `null` 并排除出汇总，文本缺失记为空串，不做补全或推断 |
| 3 | 异常值处理 | 越界时间戳剔除、负数与非有限数截断、超长文本截断；「剔除」与「截断」分开计数 |
| 4 | 数据去重 | 关注主播按 `uId`、场次按 `liveId`、记录按内容签名去重；保留信息最完整的一条，被合并行数写入 `duplicateCount` |

实测依据：关注主播接口 102 行 → 43 个唯一主播（移除 59 行重复快照，`uId=2094031249` 重复 24 次）；弹幕历史 100 场 / 512 条记录 → 5 条完全重复、117 条无 `payload` 的入场记录、176 条无 `rawText`。去重前这些站点数据会把主播数、弹幕量与标签分布整体放大。清洗报告逐源、逐项列出命中计数，可在「数据清洗」标签页展开复核；导出 JSON 仍保留**未清洗**的逐站原始结果，便于回溯。

**完整 `/analyze` 聚合画像**（`lib/analyze.js`）只消费 `cleanSessions()` 的输出，逐项对齐 `danmakus.com/analyze/{uid}` 页面的统计维度与展示结构：

- 概览指标：取回 / 有留痕 / 有互动 / 打米场次、总留痕、有效互动、弹幕数与不重复弹幕、打米总额、活跃天数、最长连续活跃、涉及主播。
- 留痕构成：弹幕 / 礼物 / 醒目留言 / 大航海 / 入场 / 禁言 / 其他，以及逐事件类型的次数与金额。
- 活跃节律：最长连续活跃、常互动时段、**7×24 时段热力图**、活跃日历、互动趋势、24 小时 / 星期 / 月份分布。（时段／星期／月份按全部清洗后留痕统计含入场；7×24 热力图按互动统计排除入场，用于节律分类。）
- 频道偏好：最亲密主播与 `loyaltyScore`、分区偏好、跨房倾向、Top1 / Top3 占比与 HHI 集中度；频道表支持名称 / 正则筛选与「隐藏仅 1 场」，**只影响显示，不改动统计**。
- 表达风格：复读指数 `repeaterIndex`、不重复弹幕比、表情弹幕 / 房间表情、平均长度、深夜发言、词云、高频词、重复文本与关键词类别。
- 支持方式分类：打米总额 / 场次 / 主播数、最多打给、打米构成、单笔最高、其他互动。
- 五维分类：核心粉丝光谱、发言表达风格、跨房倾向、活跃节律、支持方式；每张卡展示选择、置信度、完整概率分布与**驱动指标**，并附全部分类说明字典。
- 所涉直播间画像：主播标签、机构 / 个人势、粉丝量级、直播规模，明确标注「不是用户自身属性」。

### 2.8 独轮车 / 刷屏判定（v1.5.4）

「同一时间窗口内大量发送**重复或高度相似**弹幕」不再被读成「喜爱主播」，而是单独判定为**刷屏 / 独轮车**，并区分「单人主导」与「多人跟风」。判定引擎 `lib/spam.js → analyzeSpamBursts()`，弹窗与静态报告共用，结论落在两处：**用户画像总结卡**里的一行「恶意行为」+ 独立的**「恶意刷屏判定 · 独轮车」**卡（互动画像页紧跟概览指标、评论区批次页紧跟样本概览）。阈值全部集中在 `SPAM_RULES`，可整体覆盖。

**判定要素**

| 要素 | 默认阈值 | 说明 |
| --- | --- | --- |
| 时间窗口 | 主窗口 60s（滑动）；连发 10s；协同 30s | 只统计窗口内**该用户自身**的消息，窗口随消息滚动重算，任一窗口命中即取最强的一次 |
| 重复 / 相似 | 归一化后完全相等 = 1.0；否则 **二元组 Dice 与 LCS 取平均**，≥ 0.82 视为同一簇 | 归一化：全角→半角、去表情标记与标点、数字占位 `#`、折叠 3+ 连续重复字符；平均（而非取最大）是关键——只用 LCS 会把「同模板换一个字」的正常弹幕判成同簇 |
| 前缀兜底 | 短句整体是长句前缀且长度比 ≤ 2 → 0.85 | 覆盖「同一句 + 尾部语气词」；等长但末字不同（这波操作很强 / 很秀）**不给**兜底 |
| 发送量 | 疑似：窗口内 ≥ 8 条 且 同簇 ≥ 6 条 且 同簇占比 ≥ 60%；高度疑似：≥ 15 / ≥ 12 / ≥ 70% **且**（相邻间隔中位数 ≤ 1.5s 或 1s 内连发 ≥ 5 次） | 数量与速率必须同时成立；只快不多、只多不快都不升级 |
| 涉及用户数 | 同簇 ≥ 3 人且单人占比 < 50% → 改判**多人复读**；≥ 5 人各 ≥ 2 条 + 攻击/引流特征 → **跨用户协同** | 独轮车只在「单人主导」时成立 |
| 判定归属 | **按直播间主播分组各判一次**，不跨主播合并 | 独轮车是「针对某个主播」的行为；合并会稀释浓度，也会掩盖「只在 A 间刷、在 B 间正常」。实测 15 条攻击弹幕 + 另一主播 10 条正常弹幕合并后占比降到 60%，从「高度疑似」掉成「疑似」 |
| 边界修正（防误判） | 节奏慢（间隔中位数 > 10s）最高只到「观察」；同簇全是情绪 / 短句弹幕（≤ 5 字，如「生日快乐」「好听」「冲冲冲」）且无攻击特征、总量 < 20 条 → 封顶「观察」；样本 < 8 条直接不下结论 | 每次降级都会在卡的「已触发边界修正」里写明原因；带攻击词时不降级，避免把短句攻击洗成观察 |

**两条结论轴**（不合并成一个「恶意分」）

- **行为（behaviour）**：`solo` 单人重复刷屏（独轮车）/ `group` 多人复读（集体玩梗）/ `coordinated` 跨用户同步刷屏 / `none`。
- **内容（intent）**：`attack` 攻击性（辱骂 / 引战 / 引流词表命中）/ `spam` 无意义填充 / `meme` 情绪玩梗（哈哈、6、问号、单字符重复）。多人同刷同一句且无攻击特征时归 `meme`，不按「无意义填充」定性。

**等级**：`high` 高度疑似独轮车刷屏 / `suspect` 疑似 / `watch` 高频重复·观察 / `coordinated` 疑似跨用户协同 / `none` 未见异常。

**落在哪里**

- **「频道偏好 · 最亲密主播」表**：命中异常的主播，名字后面直接挂一个 pill（`独轮车` / `疑似刷屏` / `观察` / `协同刷屏`，鼠标悬停看完整判定与同簇条数）——结论跟着主播走，不用另开卡去猜是哪个直播间。
- **紧随其后的「恶意刷屏判定 · 独轮车（按直播间主播）」卡**：先是全量口径的等级与 6 项指标，再是「按直播间主播分解」表（主播 / 判定 / 同簇·窗口，按严重度排序，最多 8 行），最后两个折叠区放逐条规则与同簇样本、边界说明。
- **用户画像总结卡**：一行「恶意行为」，按最严重的那个主播定档，并写明「集中在『某主播』直播间」。
- **评论区批次页**：同一张卡跟在「样本概览」之后，口径为多用户评论样本。

**为什么不会把正常互动判成攻击**

1. 全员复读同一句梗、齐刷「生日快乐」→ 命中重复，但**不是单人主导**，判 `group` 且最高「观察」；
2. 单人齐刷短句（「生日快乐」「好听」「冲冲冲」）→ 无攻击特征时封顶「观察」，内容定性为 `meme` 而不是「无意义填充」；
3. 连刷「哈哈哈 / 666」→ 单字符重复与情绪词表归为低信息量，量不大时封顶「观察」；
4. 慢速重复（一条一条隔十几秒）→ 60s 窗口内根本凑不满 8 条，不判定；放宽窗口也会被慢速上限压回「观察」；
5. 10 条内容各异的密集发言 → 不构成同簇，`none`（已写成回归断言）；
6. 只有命中攻击词才算 `attack`，且 `attack` 只影响内容倾向，不单独提升等级。

**被攻击的主播不进「最喜爱主播」**

同一个主播不能既被判「在该直播间刷屏攻击」又被写成「最喜爱」——这会把一张卡变成自相矛盾的结论。处理方式：

- **判定条件（四条同时成立，缺一不可）**：① 该主播直播间文本足够、按主播判定成立（`suspect` / `high`）；② 行为为 `solo`（单人主导，多人跟风不算「某人攻击某主播」）；③ 同簇条数 ≥ 6；④ 内容倾向**不是 `meme`** —— 即 `attack`（辱骂 / 引战 / 引流词表命中）或 `spam`（同一句填充式刷屏）。满足者进 `spam.attackTargets`（`lib/spam.js → collectAttackTargets()`）。
  - **为什么 `spam` 也算**：v1.5.4 的立论就是「同一时间窗口内大量重复 = 刷屏，而非喜爱表达」。刷屏行为本身就在攻击那个直播间（污染弹幕、给别的主播导流），内容带不带脏字不改变性质。实测案例：在别人直播间连刷 630 条同一句引流话术「关注示例主播喵，关注示例主播喵谢谢喵」——这句不含任何辱骂词，判定是 `spam` 而非 `attack`，如果只认 `attack` 就会漏掉，导致「刷屏主播」同时挂在「最喜爱」。
  - **只有 `meme` 不剔除**：纯情绪应援（哈哈 / 6 / 问号 / 单字符重复 / ≤ 5 字短句如「生日快乐」）才是真实粉丝互动，剔除会把正常粉丝误判成黑粉。
- **移除时机**：在 `buildPortraitSummary()` 计算 `favorite` 时一次过滤——先把候选池按 `attackTargets` 剔除，再取亲密度最高的一个。因为过滤发生在数据层，弹窗总结卡、静态网页报告与导出 JSON 自动一致，不存在「某处忘了过滤」。
- **数据范围（只动候选，不动统计）**：仅影响 `summaryCard.favorite`（含由它生成的 `headline`）。频道分布图、最亲密主播指标、亲密度、Top1/Top3 占比、HHI、留痕计数、五维分类、其他主播的候选全部照旧；`channelAffinities[0]` 仍然是真正的 Top1，不会因为剔除而被改写。原文保留在 `spam.attackTargets` 与 `favorite.excluded`，导出的 JSON 里可复核「谁被排除、为什么」。
- **文案**：`favorite.text` 末尾追加「已排除被判定为攻击目标的「X」」；占比也从原来的「Top1 占比」改为「记录占比」，按**被选中的那个主播**自己算，避免拿第一名的 70% 去描述第二名。
- **不会误剔**：齐刷「生日快乐」（`meme`）这类纯情绪应援不算刷屏攻击，候选原样保留；填充 / 引流式刷屏（`spam`）与辱骂刷屏（`attack`）等价处理；若所有候选都被判定，则显示「—」并写明「候选主播均被判定为攻击目标」，不留空字段。

**口径限制**：单账号的 Danmakus 弹幕历史只有「自己」一个用户，因此只能判 `solo`；`group` / `coordinated` 需要同场多用户样本（评论区批量分析，`context: 'comment'`）。评论区结论只描述本批评论样本，不是直播间弹幕。

## 3. 技术依据与降级策略

以下结论来自 2026-11-08 的实测请求（未登录浏览器上下文），不是从文档推断：

| 接口 | 用途 | 认证 | 实测状态 | 在插件中的角色 |
| --- | --- | --- | --- | --- |
| `/x/web-interface/card` | 基础档案 | 无 | `code 0`，字段最完整 | **核心数据源** |
| `/x/relation/stat` | 粉丝/关注 | 无 | `code 0` | **核心数据源** |
| `/x/web-interface/view` | BV → aid | 无 | `code 0` | **核心数据源** |
| `/x/v2/reply/main` | 评论分页 | 无签名，但需站内 Referer | 带 Referer `code 0`；无 Referer 返回 `-352` | 评论区分析 |
| `/x/web-interface/wbi/search/type` | 昵称检索 | WBI 签名 | 签名后 `code 0` | 辅助，失败则要求填 UID |
| `/x/space/wbi/arc/search` | 投稿列表 | WBI 签名 | 签名后可用，但重复请求易触发 `412` | 增强层，失败自动降级 |
| `/x/space/wbi/acc/info` | 用户资料 | WBI 签名 | 恒 `-352` | **不依赖** |
| `/x/polymer/web-dynamic/v1/feed/space` | 动态 | WBI 签名 | `412` | **不依赖** |

关键实现决策：

1. **双通道请求**。B 站 API 的 CORS 响应为 `Access-Control-Allow-Origin: https://www.bilibili.com` 且 `Allow-Credentials: true`。因此请求优先由 `www.bilibili.com` 页面内的 content script 代发（Referer / Cookie / UA 与站内一致）；没有可用页面时降级到 service worker 直接请求。这是兼容性处理，不是修改 Origin 或规避风控。
2. **WBI 签名**。`nav` 接口即使在未登录时（`code -101`）也返回 `wbi_img`，取其文件名得到 `img_key` / `sub_key`，按固定映射表重排取前 32 位得到 `mixin_key`；参数排序、过滤 `!'()*`、UTF-8 百分号编码后计算 `MD5(query + mixin_key)` 作为 `w_rid`。Web Crypto 不提供 MD5，故在 `src/lib/md5.js` 内置 RFC 1321 实现。
3. **限速与冷却**。所有请求串行排队，默认最小间隔 900 ms + 随机抖动；命中 `-352 / -412 / -403 / -509 / -429` 时该接口冷却 60 秒，**不重试、不换 UA、不绕过**。结果按 UID 缓存 10 分钟。
4. **数据缺失不等于风险**。`card.regtime` 在绝大多数账号返回 `0`（平台未公开注册时间），因此不据此推断账号年龄、也不计入评分。任何规则在所需数据源失败时跳过并记录原因，绝不把「取不到」计为信号。

### 3.2 为什么用 `/history` 而不是 `/analyze` 的分析任务

`/analyze/{uid}?start=…&end=…` 是 SPA：HTML 只有 `<div id="root">`，真实逻辑在前端 bundle（`index-Gs-v99FY.js`、`constants-D0n6zQLI.js`、`AnalyzeRangeMenu-lgDPV_W6.js`）。调研得到的机制是：

| 机制 | 端点 / 行为 | 本插件取舍 |
| --- | --- | --- |
| API 基址 | `https://api.ukamnads.icu`，`/api/v2/`、`/api/v3/`、`users/`、`user-analysis-jobs` | 只使用 `/api/v3/users/{uid}/history` 这一个 GET |
| 服务端分析任务 | `POST user-analysis-jobs`，body `{userId, startTime, endTime, forceRefresh}` | **不调用**：POST 会在对方服务端创建任务、产生不可控写入与负载 |
| 任务状态 | `GET /{jobId}`，`GET /{jobId}/events`（EventSource：`created / queued / indexing / loading / aggregating / completed / failed / canceled`） | 不引入轮询 / SSE 状态机 |
| 任务结果 | `GET /{jobId}/result`，返回 MessagePack（`application/x-msgpack`） | **不解码**：避免新增二进制依赖，且结果含不可复核的主观性格标签 |
| 原始记录 | `GET /history`，`items[].danmakus` 是对象 `{actors, roomEmojis, records}`，`records[]` 含 `ts / type / actorId / payloadKind / payload.rawText` | **采用**：纯 GET，本地重算统计 |

其他实测结论：

- `start/end`、`startTime/endTime` 对 `/history` **不生效**（这些是 `/analyze` 页面提交 POST 任务的参数），所以日期范围改在扩展本地按 `ts` 过滤。
- `hideOnlyEnter` 显著改变 `total`：某样本 UID（已脱敏）实测 `true` → 33 场、`false` → 102 场。因此该开关与「样本口径」一起显示在界面上。
- 默认只取前 2 页 × 50 场次，最多 5 页；`hasMore` 为真时明确标注「样本非全量」。

### 3.2.1 机构名解析（v1.3.1）

弹幕记录里的 `channel.agencyUuid` 有三种取值：`independent`（站点对「无机构个人势」的固定枚举）、`null`（未标注）、以及**机构 UUID**（如 `ad652370-a736-537f-aa70-6ee528138364`）。实测 v3 没有机构路由，而 **v2 提供公开字典端点**：

```text
GET https://api.ukamnads.icu/api/v2/agencies/{uuid}      # 单个机构：{code:200, data:{uuid, name, description, groupType, memberCount}}
GET https://api.ukamnads.icu/api/v2/agency-options       # 全量字典：[{uuid, name, memberCount}, ...]，independent 的官方名称即「独立个人势」
```

处理方式：清洗层把 `independent` 归一化为「个人势」、缺失记「未标注」并保留原始 `agencyUuid`；聚合层对取回场次中出现的机构 UUID 逐个调用 v2 端点解析名称（24 小时缓存、间隔 300ms、失败保留 UUID 并计数，不因字典缺失丢弃画像数据）。样本验证：`ad652370-…` = **chucolala**（Paryi 组建的社团）。Danmakus 官方前端的显示规则一致：`uuid === 'independent' ? '个人势' : agencyName ?? uuid`。

v1.3.1 同时修正三处易误读的口径标注：

1. 「关注主播」表的弹幕 / 场次列是**主播频道级累计值**（该主播开播以来全部弹幕与场次），不是目标用户的行为；列头已改为「主播累计弹幕 / 主播累计场次」并加说明。
2. 「所涉直播间画像」的观看 / 付费指标统一加「直播间」前缀；明确「累计口径」与「场均口径」不可比较——「直播间累计付费人次」高于「直播间场均观看」是口径差异，不是数据错误。
3. 「留痕构成」加注：默认「隐藏仅入场场次」会把只留入场记录的场次整体排除（实测某样本入场记录 117 → 45），礼物计数减少来自去重（同一内容签名只计一次），均非数据丢失。

### 3.3 参考 `files.danmakus.com/danmaku-history.js` 的核对结论

该脚本是 Danmakus 提供的 B 站「弹幕历史」组件（`@bevo/core` 组件机制，`coreVersion 2.7.0`），会在用户卡片、个人主页、动态主播卡与直播弹幕菜单注入一个分页面板，请求：

```text
GET https://ukamnads.icu/api/v2/user?uid={uid}&useEmoji=true&pageSize={n}&pageNum={page}   // pageNum 从 0 起
```

2026-11-08 逐个实测后确认，它与我们使用的 v3 端点是**同一批数据的不同序列化**：

| 项目 | v2 `/api/v2/user` | v3 `/api/v3/users/{uid}/history` |
| --- | --- | --- |
| 域名 | `ukamnads.icu` | `api.ukamnads.icu` |
| 场次列表 | `data.data.records[]` | `data.items[]` |
| 每场弹幕 | `danmakus[]` 扁平数组 `{uId, uName, type, sendDate, message}` | `danmakus` 对象 `{actors, roomEmojis, records:[{ts, type, payload.rawText}]}` |
| 分页 | `pageNum`（0-based） | `page`（1-based） |
| `hideOnlyEnter` | 同样生效 | 生效 |
| `start/end`、`startTime/endTime` | 不生效 | 不生效 |
| 某样本 UID 的 `total` | 102 / 33 | 102 / 33 |
| `channel` / `live` 字段 | 完全一致 | 完全一致 |

首条场次的主播（名称已脱敏）、`liveId`、时间戳与弹幕文本在两个端点逐字一致，总量口径也一致。

**该组件脚本本身已过时，不能直接搬运**：

1. 它把 `data.data.records` 当作弹幕数组渲染，但服务端现在返回的是**场次列表**；弹幕在每场的 `danmakus` 数组里。
2. 它读取 `data.data.watchedChannels`，实测该字段已不存在。
3. 其 `DanmakuType` 枚举只到 9（`Block`），缺少 v3 的 10–13（警告 / 录制开始 / 录制中断 / 主播）。

本项目的处理：

1. 主通道继续用 v3，**不请求 `ukamnads.icu`，因此不新增该域名的 host permission**。
2. `parseDanmakusHistory()` 同时兼容 v2 的 `data.data.records` 容器与扁平 `danmakus[]` 结构，改版或将来切换端点时解析器不会失效（`verify.mjs` 用 v2 样例做了回归）。
3. 从两个版本共有的 `channel` / `live` 字段中提取主播标签、粉丝量级、机构类型与直播规模，落地为「所涉直播间画像」，并明确标注这不是用户自身属性。
4. 未使用 `useEmoji` 表情替换逻辑，也未采用任何服务端主观性格标签。

### 3.4 Bilibili Evolved 用户组件的加载机制与实现

查证的是 Evolved 官方仓库（`the1812/Bilibili-Evolved`，`master` 分支）的源码，而非猜测格式：

| 依据 | 结论 |
| --- | --- |
| `CONTRIBUTING.md` | 组件源码位于 `registry/lib/components`，入口 `index.ts` 导出 `component`，推荐用 `defineComponentMetadata` |
| `src/components/types.ts` | `ComponentMetadata` 必含 `name` / `displayName` / `tags` / `entry`；`urlInclude` / `urlExclude` 为 `(string \| RegExp)[]`；入口签名为 `({ settings, metadata, coreApis })` |
| `src/components/define.ts` | `defineComponentMetadata` 只是恒等函数，因此**直接导出普通对象即可**，无需依赖 `coreApis` |
| `src/core/external-input/load-feature-code.ts` | 用户代码在 `with(window)` 沙箱里 `eval`；取注入 `exports` 的**第一个值**作为元数据，或取整段表达式的返回值 |
| `src/core/install-feature.ts` | `isComponent = Boolean(item?.entry)`，露出 `entry` 才会被识别为组件（否则按插件 / 样式处理） |
| `src/components/user-component.ts` | 安装时用 `lodash.omit` 去掉函数字段后持久化 `metadata`，保存 `code` 与 `settings` |
| `src/components/component.ts` | 加载时调用 `component.entry({ settings, metadata, coreApis })`，返回值存入 `loadedComponents` |
| 官方编译产物 `registry/dist/components/utils/active-video-links.js` | webpack UMD，`globalThis` 兜底，末尾导出 `component` |

据此，组件产物是一个**自包含单文件 IIFE**：`build-evolved.mjs` 把 `src/lib/*.js` 按 `md5 → wbi → clean → analyze → profiler → federated` 的拓扑顺序改写成同一作用域内的 IIFE 模块，前面插入运行时适配层，后面接组件主体。**两条导出路径同时生效**：既写入 `loadFeatureCode` 注入的 `exports`（取第一项），也让整段代码作为表达式返回组件元数据（取 eval 完成值）。刻意不写经典 UMD 的 `module.exports` 分支——B 站页面可能已存在全局 `module`（webpack chunk），误判成 CommonJS 反而会让 Evolved 取不到导出值；`verify-evolved.mjs` 专门覆盖了这个冲突场景。因此组件与扩展**共用完全相同的清洗层、完整画像引擎、多源解析器与规则评分代码**，不存在两套口径。

运行时适配层只替换环境相关的三件事：

- `fetch` → 优先 `GM_xmlhttpRequest`（可跨域、带 Cookie、`abort` 支持），不可用时降级到页面原生 `fetch`；返回 `fetchOne()` 需要的最小 `Response`（`status` / `ok` / `text()`）。
- `cacheGet` / `cacheSet` → 内存 `Map` + `localStorage`，TTL 语义与扩展 `store.js` 一致；`clear-cache` 只清 `bililens:evolved:*` 前缀。
- UI → Shadow DOM 浮动按钮 + 五个标签页（画像概览 / 完整弹幕画像 / 多源数据 / 数据清洗 / 设置与导出），自带样式不污染 B 站页面。

组件不申请任何扩展权限，不读写 `chrome.*`，不请求 `ukamnads.icu`（仍只走 v3 端点），不调用 POST 分析任务。`verify-evolved.mjs` 用 `vm` 复刻 `loadFeatureCode` 的沙箱，配合真实研究样本端到端验证 UMD 导出、元数据判定、五个标签页与清洗后口径（102 → 43、移除 59）。

## 4. 画像口径与可复核性

严格区分三层，避免把统计量误当成结论：

| 层 | 内容 | 例子 |
| --- | --- | --- |
| `facts` | 接口返回的可复核原始事实 | 等级、粉丝数、`record.ts`、`record.type` |
| `derived` | 由 facts 计算的统计量 | 标题模板率、24 小时分布、最长连续活跃天数 |
| `inference` | 规则命中（线索优先级） | R03 标题模板化 +18、F01 第三方样本时段集中 +8 |

设计约束：

1. `profile.federated` 与弹幕行为统计是**独立证据层**，不改写官方 `facts`，默认不参与评分。
2. 所有时间统一按 UTC+8 自然日分桶；趋势图纵轴为该 UID 自身样本范围，不做跨账号归一化。
3. 缺失显示 `—` 或标记 `page_only`，不推断为 0；取回场次但日期筛选后无记录记为 `page_only` 而非「有数据」。
4. 重复文本只做归一化计数，不输出「刷屏」「水军」「同一人」等事实性判定。
5. 主播标签、粉丝量级、机构类型与直播规模是**所涉直播间**的属性，按主播去重、只统计筛选后仍有记录的场次；界面与导出均带「不是用户自身属性」的警示，不据此推断用户身份、消费能力或立场。
6. 报告 `limitations`、`settingsEcho`、`rawResults` 与 `statuses` 保留完整采集口径，便于逐条回溯。
7. **v1.3.0：所有图表与分类卡只消费清洗后的数据**。清洗工序固定为「字段规范化 → 缺失值处理 → 异常值处理 → 数据去重」，逐项计数写入 `cleaning`；`livePortrait.dataBasis` 与 `federated.dataBasis` 均为 `cleaned`，弹窗据此断言，不满足时跳过渲染。导出的 JSON 同时保留未清洗的逐站原始结果，保证「可复核」不被清洗破坏。

## 6. 已知限制

1. **未登录 / 未打开 B 站页面时**，WBI 增强接口与评论接口可能返回 `-352` 或 `412`；核心的 card / relation / view 通常仍可用。界面会逐项显示数据源状态。
2. **投稿列表不稳定**，重复请求易触发 412，此时 R02–R04、R06、R07 会被跳过并标注原因，评分覆盖度下降。
3. **评论分页**使用服务端返回的 `cursor.next` 作为下一页游标（不按页数自增），最多 10 页；平台改版或风控时可能提前终止，报告会记录告警。实测短时间内连续请求该接口会触发 `-352`，因此默认 900 ms 节流是必要条件而非可选调优。
4. **批量分析有样本上限**（默认 12 人），按评论出现顺序取样，不代表评论区全体。
5. **不做账号年龄推断**：`regtime` 普遍为 0；也不做头像「是否默认图」这类不可靠判断。
6. 扩展仅在本机处理数据，但多源聚合会向目标站点发出请求，对方可能记录你的访问。
7. **多源数据不受本工具控制**：八个查询项的数据口径、更新频率与可用性由第三方决定；AICU 存在滑块与 `code=-429` 软限流，`api.zeroroku.com` 实测不可用（改用页面 Nuxt 数据），`matsuri.icu` 纯客户端渲染无法结构化提取，VTBs 只收录 V 圈账号。界面会逐站标注 `data / page_only / not_listed / cooldown / error`。
8. **第三方样本不是全量**：AICU 只取第 1 页 20 条样本，「历史评论总量」是站点自行标注的数字；弹幕记录最多取 5 页 × 50 场次。所有时间分布图只描述这批样本，不能外推为账号整体行为规律。
9. **弹幕日期筛选是本地的**：服务端 `/history` 忽略日期参数，设置日期范围不会减少网络请求量，只会减少参与统计的记录；界面同时显示筛选范围与 `hasMore` 状态。
10. **弹幕重复文本归一化会有噪声**：不同句子折叠后可能合并，同一句加表情 / 数字也可能被归为同一类；列表只作为人工复核入口，不作为判定依据。
11. **所涉直播间画像易被误读**：主播粉丝量、直播观看人次与付费人次属于主播/场次，不属于目标用户；聚合值按场次累加、主播维度按主播去重，只统计筛选后仍有记录的场次。界面已用警示文案标明，解读时仍需回到逐站原始结果。
12. 一次多源聚合会串行访问最多 7 个查询项（约 5–8 秒，弹幕多页时更长），重复点击「强制刷新」会增加对方站点负载，请按需使用；命中风控后该站点冷却 60 秒且不重试。
13. **Evolved 组件依赖脚本管理器的 `GM_xmlhttpRequest` 做跨域取数**；若管理器未注入（或组件代码运行在普通网页上下文），会降级为页面原生 `fetch`，此时第三方站点可能因 CORS 取不到数据，界面会逐站显示失败状态而不是伪造结果。B 站官方接口在同域页面上通常仍可用。
14. **Evolved 组件未做评论区批量分析与 WBI 增强层**：它聚焦单 UID 的官方档案 + 多源聚合 + 完整弹幕画像；`scoreProfiles()` 的评论相关规则因缺少评论样本会被标记 `skipped`。需要批量评论分析请用扩展形态。
15. 组件与扩展**各自独立缓存、互不同步**：组件写 `localStorage` 的 `bililens:evolved:*`，扩展写 `chrome.storage.local` 的 `bililens:*`。两者同时运行会对同一站点各发一次请求。

## 7. 合规边界

- 只读取 B 站公开接口、你自己浏览器上下文中的公开数据，以及 `manifest.json` **白名单**内已列明的第三方公开端点；v1.2.0 起**不再申请任何跨站通配符权限**（`optional_host_permissions` 已移除）。
- 已核对 Danmakus 官方组件使用的 v2 端点（`ukamnads.icu`），但**不请求该域名、不为其申请权限**；解析器兼容其数据结构仅用于服务端改版时兜底。
- **不读取、不保存 Cookie / SESSDATA / token**；多源请求一律 `credentials: 'omit'`。
- 不调用第三方服务端的 POST 分析任务，不提交表单，不写入任何第三方数据；弹幕统计全部在扩展本机完成。
- 不批量高频抓取、不重试风控请求、不伪造或删除请求头以规避平台风控。
- 不确定任何自然人身份，不输出「水军」「同一人」等事实性判定；评分只用于安排人工复核的优先级。
- 多源聚合会向八个查询项发出 GET 请求，对方可能记录你的访问。请求只在用户主动点击后串行发出，命中风控即冷却 60 秒且不重试，可只清除多源缓存。
- 第三方数据只作为可复核的证据与可视化素材，不改写官方事实、不默认参与评分；站点口径、时效性与准确性由各站点自行负责。
- 遵守 B 站及目标站点的服务条款与适用法律；所有结论须回到报告中的原始证据逐条核验后再使用。
- **Evolved 组件形态**：不申请扩展权限、不使用 `chrome.*`，仅按 UID 读取同样的白名单站点公开端点；`GM_xmlhttpRequest` 由用户已安装的脚本管理器提供并遵循其 `@connect` 授权策略；缓存只写本机 `localStorage`，不上传。组件同样不登录、不保存凭证、不重试风控请求、不做去匿名化人肉。
